## Goal

既存検知器の見逃しに時間構造の欠落が関係し、時間特徴の追加が厳しい正常条件でも有用か検証する。直近では「どの検知器の、どの条件の、どの見逃しを説明するか」を固定する。

## Current Hypothesis

- H1: 時間構造を補うことで、既存統計量が捉えない見逃しを改善できる。
- H0a（競合）: 見逃しは実装版・数値尺度・入力scope・時刻やラベルの不一致に起因する。
- H0b（競合）: packet gate、閾値下限・更新、score条件等の単純変更だけで十分改善できる。
- H0c（競合）: 時間特徴は正常周期通信や通常の輻輳も拾い、LDoSを区別する追加価値を持たない。

いずれも現在の結論ではない。H0aの切り分けを先に行う。

## Evaluation

まずP1-G0では入力・版・ラベル・結果の対応を検証する。以降の分類評価では同一入力・同一校正データを使い、既存方式、単純変更、時間特徴単独、既存＋各時間特徴を比較する。

- 条件: 通常TCP、厳しい正常輻輳、正常periodic、無選別random burst、periodic LDoS。後続Gateでjitter等の範囲を追加する。
- Recall、FPR、Precision / F1、混同行列、分母、run/seed数。train/validation/testはrun単位で分離し、testで閾値を調整しない。
- Detection latencyは攻撃開始から初回判定までとし、未検知を0扱いせず件数と併記。起動待ち・未定義率・欠測の扱いを明示する。
- Feature calculation cost、CPU / memory costは実験PCで同一入力・測定区間・ログ条件を揃えて比較する。Pythonオフライン速度からXDP性能を断定しない。
- TCP goodput、再送等を併記し、性能低下一般とLDoS固有の識別を分ける。

## Success Criteria

- **現在のP1-G0:** 少なくとも一つの対象版・実データ条件について、run→入力→設定→解析→結果を辿れ、再解析が保存結果と事前に定めた許容差で一致する。不一致の説明・未回収条件も残す。対象がP0なら結論もP0に限定する。
- **後続Gate:** 許容FPR、必要Recall改善幅、最大検知遅延、計算・CPU・memory予算、必要試行数・不確実性の扱いを、確認評価の前に実験計画へ数値で固定する。現在は未設定であり、性能についてGOとは判定しない。
- 独立評価と厳しい正常条件で基準を満たす場合だけ採用候補とする。単純変更で十分な場合も有益な結果として認める。

## Stop / Reconsider Conditions

- 版・時刻・ラベル・入力が対応しない場合は原因や元手法の限界の主張を止め、証拠回収に戻る。
- 単純変更で同等の結果が得られる場合は時間特徴追加を再考する。
- 正常periodicのFPR悪化、jitterへの過敏性、特定seedだけの改善、許容外のコストがあれば修正／棄却する。
- 正常輻輳と区別できない場合、LDoS固有信号とは扱わない。negative resultを残す。
- データ不足・未測定は失敗の証明でもGOでもない。不足情報と、その間に可能な最小作業を記録する。

## Next Decision Gate

**P1-G0: 対象検知器・実行条件と見逃し結果の対応を確認できたか。**

- GO: 根拠となるrun/解析/ログentryを記載し、P1-G1の単純変更による原因切り分けへ範囲を更新する。
- REVISE: 不一致があれば入力契約・実行仕様の照合へ戻る。既存判定の変更が必要なら別profileとして区別する。
- 未判定: PCAPや設定が不足する場合は回収一覧と再実行手順を整備し、Gateを維持する。
- NO-GO: 対象条件を再構成できないと判断した場合は、その結果を主張の根拠から外す理由をログに残し、新しい再現可能な条件を計画する。

Gate更新時は日付・根拠entry・判断・新しいImplement Now / Do Not Implement Yetを揃えて更新する。
